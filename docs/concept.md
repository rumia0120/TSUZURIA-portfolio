# TSUZURIA

**一行コンセプト**　友達と一冊の日記を順番に回し、自分のペースで日常を伝え合うWebアプリ。

## 1. なぜ作るのか

紙の交換日記をヒントに、友人同士で、特別な用事がなくても近況を伝え合える場を作りたい。みんなが同じ時刻に集まる必要はなく、日記が回ってきたときに、自分のペースで書くイメージ。

LINEでは用事や話題がないと連絡するきっかけが生まれにくい。個人用のメモや日記は、自分のために書くことが多い。SNSでは、周りの投稿や決まった投稿時刻が気になることもある。TSUZURIAでは、自分の番が来ることを近況を伝えるきっかけにして、友人の普段の生活や考えていることを少しずつ知れるかを確かめたい。

## 2. 誰のためか

まずは、普段からつながりのある友人同士を想定する。身近な友人に加え、ネットで知り合った友人とも使える場面を考えている。MVPでは、友人3〜5人で一冊の日記を回す。

想定するのは、用事がなければ連絡しづらかったり、SNSでは日常の一部しか出せなかったりする人。たとえば、AIやプログラミングのように、自分にとって大切でも友人とは普段話すきっかけが少ないことを、日記なら自然に書けるかもしれない。

## 3. どんな体験にしたいか

- その日にしたことや頑張ったことを、自分の言葉で友人に伝えられる。反応が返ってくるかにかかわらず、自分にとって大事なことを表現できたと感じてほしい。
- 友人の投稿に共感したときは、気軽に気持ちを返せるようにしたい。書いた人が無視されたと感じにくく、読む人も反応を急かされない体験を目指す。
- 日記は決まった順番で回し、自分の番が来たら都合のよいときに書く。利用場面は19〜22時ごろの夜を想定し、1回10分以内で書いて渡せることを目安にする。
- 日常に取り入れやすいよう、開く・読む・書く・反応するそれぞれの手間を減らす。操作の負担が理由で使わなくなることを防ぎたい。

## 4. 最初に作る機能

まずはログインが必要なWeb版を作る。3〜5人のグループで、招待から参加、日記の作成、次の人への受け渡し、閲覧までの流れを作る。

| 機能 | 想定する役割 |
| --- | --- |
| アカウント・ログイン | アカウントを作り、名前を設定してログインする。 |
| グループ | 一緒に使う友人を招き、日記を回す相手を決める。 |
| 日記の作成・受け渡し・閲覧 | 日記を書いて次の人に渡し、回ってきた日記を読む。 |
| リアクション | 数種類のスタンプや絵文字から選び、ワンタップで気軽に反応できるようにする。 |
| メール通知 | 日記が回ってきたことをメールで知らせる。 |

### 初版に入れるか検討中の機能

- 受け渡しのルール。1日1回の上限、一定時間後のスキップ、返信までの待ち時間を設けるか検討する。
- 音声入力。文字で書く負担を減らす手段として検討する。

## 5. 初版で作らないもの

- 2人用の交換日記。対応は後回しにする。
- 写真の添付。住所や行動範囲が伝わるリスクと、実装の負担を考慮する。
- Webプッシュ通知。MVPではメール通知を使う。
- スキップ回数の制限。対応は後回しにする。
- アプリ内のAI機能。AIは開発に使う。
- スマートフォン向けのネイティブアプリ。Web版の後に検討する。
- DM（個別メッセージ）。グループで招待し、日記を回す流れを優先する。
- ブロック機能。現時点では初版から外す方針。退出や共有停止の扱いは「守りたいこと」に記載する。

## 6. 見た目と雰囲気

画面には紙の交換日記を思わせる雰囲気を出し、使うこと自体が楽しみになるような、洗練された見た目にしたい。具体的な参考アプリは未定。Mac、Grok、Claudeのデザインや、それぞれに一貫した雰囲気があることが好み。色や画面の言葉づかいは今後決める。

## 7. 守りたいこと

- 共有する前に誰が読めるかを確認できるようにし、日記がグループ外に見えないことをダミーデータで確かめる。ネットで知り合った友人との利用では、日記の内容から住所や行動範囲が伝わることにも気をつける。
- 利用テスト前に、退出や共有停止の方法と、退出後に共有済みの日記がどう扱われるかを決める。参加者には、試験の目的と期間、収集するデータ、閲覧できる人、削除方法、問い合わせ先、未完成の機能や制約を伝え、同意を得る。
- メール通知が執筆を急かさないか、リアクションを返すことが負担にならないかを確かめる。

## 8. ゴールと検証

- 2027年3月末までにWebアプリを公開することを目指す。
- 最初は、すでにつながりのある友人同士の少人数グループで試す。その先の利用者数の目安は約50人。
- 利用テストでは、グループごとの受け渡し回数と、途中で止まった理由を確認する。参加者には、普段は話さない近況を伝えられたか、安心して書けたかを聞く。日常に取り入れやすかったか、ワンタップで気軽に反応できたかも聞く。

## 未確認の質問

- 招待はどう送り、誰が参加を承認するか。投稿ごとに誰が読めるか。途中参加した人は過去の日記を読めるか。
- 日記を回す順番は誰がどう決めるか。検討中の機能のうち、どれを初版に含めるか。
- メール通知はどのタイミングで送るか。利用者が止めたり頻度を変えたりできるか。
- リアクションにはどんなスタンプや絵文字を用意するか。
- 個人情報を書きすぎないよう、投稿時にどんな案内を出すか。退出、共有停止、通報、退会、投稿の保持・削除はどう扱うか。
- Web版の公開範囲をどこまで広げるか。公開までにどの機能と安全対策が揃えば完成とするか。
- 利用テストの期間、同意・削除方法、評価基準はどう決めるか。約50人はどの時点の、どんな利用状態を指すか。
- 収益化は考えるか。考える場合、いつ検討するか。
