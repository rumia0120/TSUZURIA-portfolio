# TSUZURIA の決定・検討記録

プロダクトの目的とMVPの全体像は [concept.md](concept.md) を参照する。本人が決めたことは、日付ごとに決定内容と「なぜそう決めたか」を記録する。理由がまだ確認できていない場合は、その旨を記し、確認できた時点で追記する。

## 2026-11-12

### 決まっていること

- MVPでは友人3〜5人で一冊の日記を順番に回す。ワンタップのリアクションを用意し、自分の番が来たことをメールで知らせる。
- 2人用、写真添付、Webプッシュ通知、スキップ回数の制限は初版の対象外。写真は住所や行動範囲が伝わるリスクと実装負担を考慮して見送る。

### 技術スタック

- Next.js、TypeScript、Tailwind CSS でローカル開発環境を構築済み。Supabase は認証・データベースの第一候補で、SDK と環境変数のひな形を用意済み。実際のプロジェクトへの接続は未実施。
- 技術の選定では、MVPに合うこと、求人で求められる技術との接点、就職活動で設計・実装・検証の理由を説明できることを考慮する。

### 日記の閲覧・保持ルール（検討中）

| 論点 | 現時点の案と理由 |
| --- | --- |
| 自分の番が来る前の閲覧 | 共有済みの日記は、閲覧権限のあるメンバーなら自分の番を待たずに読んでリアクションできる案。書く順番を守りつつ、都合のよいときに読める。 |
| 途中参加者の閲覧範囲 | 参加後に共有された日記から読める案。書いた当時に想定した読者の範囲を守るため。参加前の日記をどこまで見せるかは未決定。 |
| 閲覧期限 | 閲覧できる日記に一律の期限を設けず、振り返れるようにする案。半年などで閲覧を区切るかは未決定。 |
| 退出後の閲覧と投稿 | 退出した時点でグループの日記への閲覧権限を止める案。本人の共有済み投稿をグループに残すか、どう削除できるようにするかは未決定。利用テスト前に決め、参加者に伝える。 |

閲覧ルールを実装するときは、現在の担当、メンバーの参加・退出時点、日記の共有時点を区別する。招待方式と日記を回す順番の決め方も引き続き検討する。

### データ設計を自分の言葉で説明する

- **プロフィール（`profiles`）**。利用者1人の表示名。アプリ内で呼ばれる名前を持つ。
- **グループ（`diary_groups`）**。日記を回すグループの名前と、今だれの番かを持つ。
- **所属（`group_members`）**。1人が1つのグループに参加した記録。グループ内で何番目に書くかと、参加・退出の日時を持つ。たとえば A → C → B の順番は所属に記録し、今がCさんの番なら、その担当はグループに記録する。
- **日記（`diary_entries`）**。1回分の本文、書いた人、作成日時（`created_at`）、共有日時（`shared_at`）を持つ。共有日時が空なら下書きで、所属中の作成者本人だけが読める。
- **リアクション（`diary_reactions`）**。誰がどの日記にどんな反応を付けたかを記録する。試作では同じ日記に1人1件まで。別の日記にはそれぞれ付けられる。

試作では、所属の参加日時と日記の共有日時を比べて、途中から参加した人が読める日記を決める。参加日時を記録するのは、この閲覧範囲の判定にも使うため。

### 画面デザインの方針

- **手書きの雰囲気がある、すっきりした画面を試す。** 最初の案は、本人にはAIで作ったと分かるような見た目に感じられた。Claude や Claude Code の落ち着いた雰囲気と手書き風の文字が好みなので、試作では生成りと朱色を使い、ロゴを手書き風にした。
- **本文はノートの紙面を思わせる見た目にする。** 最初の案は本のように見えたため、普段使うノートの感じを出したい。試作では横罫と左の余白線で表現した。

## 2026-11-13

### ログインと日記の閲覧を自分の言葉で説明する

1. **ログインする。** Supabase Auth がメールアドレスとパスワードを確認する。成功すると、アプリはその人のログイン情報（セッション）を使ってDBに問い合わせられる。
2. **所属グループを選ぶ。** DBはセッションから分かるユーザーIDで所属を確認し、参加中のグループ一覧を返す。利用者はその一覧から「週末の交換日記」などを選ぶ。所属の確認に使うのはユーザーIDで、メールアドレスやパスワードは所属先に渡さない。
3. **日記一覧を見る。** DBの行レベルセキュリティ（RLS）が、所属と参加日時、日記の共有日時に基づいて、読める共有済みの日記を返す。
4. **本文を開く。** アプリは日記IDを指定して「ログイン中のこの人に、この日記1件を返してよいか」とDBに問い合わせる。DBは一覧と同じルールで判断するので、別グループの人が本文URLを直接開いても本文は返らない。

ユーザーIDはアカウントを識別するための値。元のパスワードを取り出すことはできない。開発環境では、別グループのテスト用アカウントで本文URLを開けず、そのアカウントでDBに問い合わせても0件だったことを確認した。 [画面と取得処理](../app/diary-reader.tsx) · [DBの閲覧ルール](../supabase/migrations/20261112122409_diary_prototype.sql)

## 2026-11-15

### グループ作成と招待を自分の言葉で説明する

1. **グループを作る。** 日記一覧の手前にある「マイグループ」で「グループを作る」を押し、名前を入力して「作成する」を押す。DBがグループを作り、自分を最初のメンバーとして登録する。
2. **友達にリンクを渡す。** 作成したグループの画面で「招待リンクを発行」を押し、URLをコピーして友達に渡す。1本で1人が参加できるので、2人を招待するなら2本発行して1本ずつ渡す。リンクは発行から7日間使える。
3. **友達が参加する。** 友達がリンクを開き、ログインして「参加する」を押す。DBがリンクの期限と使用状況、すでに参加しているか、グループに空きがあるかを確認して参加を確定する。作成者を含めて3人そろうと、作成者から参加順に日記を回せる。上限は5人。

`create_diary_group`、`create_diary_invite`、`accept_diary_invite` は、画面からDBに処理を頼むときに使う関数名。`diary` は「日記」の意味。

| ボタン | DBに頼む処理 |
| --- | --- |
| 作成する | `create_diary_group` でグループを作り、作成者を登録する。 |
| 招待リンクを発行 | `create_diary_invite` で作成者かを確認し、招待コードを発行する。 |
| 参加する | `accept_diary_invite` で招待コードを確認し、ログイン中の人をメンバーに登録する。 |

現在の確認用URLでは、アプリのログイン画面を開く前に Vercel の認証がかかる。実際に友達が試すには、アプリのログインに加えて Vercel 側のアクセスも必要。

### 新規登録のあとにログインを案内する

登録フォームの送信後は、確認メールが届いた場合の手順と、すでにアカウントを持っている場合の「ログインへ」を、同じ案内に表示する。登録済みの人がメールを待ち続けずに済み、第三者が画面の表示から特定のアドレスの登録状況を判断できないようにするため。

### 退出したときの日記と順番

- 退出した本人は、そのグループの日記を読めなくなる。本人が共有していた日記も、残っているメンバーから見えなくする。ネットで知り合った友達と使う場合にも、自分の書いた個人情報をこれ以上グループに見せたくないときに退出で共有を止められるようにするため。
- 退出した人が今の担当者で、3人以上残る場合は次の人に進める。担当者以外が退出した場合は、今の担当を引き継ぐ。
- 3人未満になったら日記の受け渡しを止め、再び3人そろったら保留していた番から再開する。友達3〜5人で回すという前提を外れた状態で、日記を送らずに待てるようにするため。

退出前の日記は、同じアカウントで再参加しても共有に戻らない。グループで読める範囲を変更する実装で、保存期間と完全削除の方法は別途検討する。

実装では、招待を担当していた人が退出した場合、書く順番が先頭の残存メンバーに招待権限を移し、未使用の招待リンクを無効にする。残った人が新しい友達を招待して日記を再開できるようにするため。

### 気軽に押せるリアクション

- 日記の本文下に「いいね」「にっこり」「応援」を置く。読むたびにどれを選ぶか悩まなくて済むように、広い気持ちで使える「いいね」を先頭に置く。絵文字と短いラベルを組み合わせ、日記と同じノート風の配色を使う。
- 1人が日記1件につけられる反応は1つ。同じボタンで取り消し、別のボタンで変更できる。返信を書く余裕がないときにも、気軽に気持ちを伝えられるようにするため。
